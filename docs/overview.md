# memex 概览

> 讲 memex 怎么运作、为什么这么设计(理解导向)。要看模块地图、改某类东西去哪个文件 → [architecture](architecture.md);逐条用法 → `memex --help` / `memex-sync --help`。本文不讲安装、不列字段、不复述 codemap。

## 它解决什么

知识不是攒在一个地方的。它散在十几个独立的源仓里——每个仓按自己的领域组织一堆 markdown note。当你想找「之前那个关于 X 的结论」,问题不是「某个仓里有没有」,而是「**全部仓加起来,哪几条最该现在看**」。

memex 是这堆散落知识的检索引擎:把所有源仓的 note 编译进一个中央索引,对外只给**一条最佳召回**。它是 **local-first** 的——索引、检索、telemetry 全在本机,没有云端检索服务;唯一的外部依赖是一个本地 embedding 服务和一个本地向量库。

它**只做召回**,不裁判 note 正文写得对不对(那是上游 authoring 工具的事),也不存源仓清单的真相(那在引擎外面)。引擎的职责很窄:**给定一个 query,从合规的已编译产物里排出最该看的几条**。这条边界让引擎对任何人的 KB 都通用——你的知识是数据,引擎是引擎。

## 几个概念

**三条 lane 并存,因为没有一种检索对所有 query 都对。** memex 同时备着三种召回方式:

- **lexical**(BM25 关键词):你搜一个确切的代码符号、一个专有名词、一个 ID,词面命中就是最强信号。lexical 对「强锚定」的 query 几乎不可替代——语义相似度反而会把一个长得不像但意思相近的东西排到前面,挤掉那个你**确切**要找的。
- **semantic**(向量相似度):你用一句自然语言描述一个意思,但记不得原文用了哪个词。这时词面对不上,只有语义对得上。中文尤其吃这条 lane——分词碎、同义表述多,纯关键词容易空手而归。
- **hybrid**:把前两条的排序融合成一条。

**为什么不二选一**:强锚 query 要 lexical 兜底,模糊 query 要 semantic 补位。任何单 lane 都会在另一类 query 上系统性地塌掉。三条并存不是堆功能,是承认「检索」本来就有两种相互冲突的需求。

**加权 RRF:融合两个排名,而不是融合两个分数。** lexical 的 BM25 分和 semantic 的余弦相似度量纲不同、不可直接加。memex 用 Reciprocal Rank Fusion——只看每条结果**在各 lane 里排第几名**,贡献 = `weight / (K + rank)`,再相加。直觉:一条结果在两条 lane 都靠前,融合后必然靠前;只在一条里靠前的,得看那条 lane 这次该多信。

「该多信哪条」就是权重在做的事,而且是**按 query 自适应**的:一句中文低锚 query(有中文、没有代码标识符 token)→ 抬高 semantic 权重,因为词面靠不住;一个强锚定 query(多个代码符号 token)→ 抬高 lexical 权重,因为词面就是答案。权重不是全局调出来的一个数,是 planner 当场看 query 长什么样决定的。

**recall:对外只有一个最佳召回,不是一把参数。** 引擎内部能调的旋钮很多——选哪条 lane、各 lane 取多深、protection 开不开。但对外暴露这些等于把调参负担推给调用方,而**绝大多数调用方(包括 agent)只想要「最该看的几条」**。所以 memex 把生产验证过的最佳配置锁进一个 `recall` 入口:hybrid + 一项保护策略 + 标题/路径富化。底层的 `query` 还在,留给做评测、调参、单 lane 诊断的人;但日常召回只走 `recall`。**取舍**:换配置不再是改一个调用参数,而是动引擎默认——这是有意的,因为「最佳召回」该是引擎的承诺,不是每个调用点各自的猜测。

**编译 + sync:写路径把 note 变成可检索的点。** 一条 note 不是直接进索引的,中间隔着「编译」。编译把源仓的 markdown 投影成一个稳定 schema 的已编译文档,顺便做一道闸门:**有 frontmatter 才可索引,没有就大声跳过并记进报告**(不是静默丢弃——你要能看见什么没进去)。编译产物落在中央数据目录,源仓零污染。然后 sync 把这些产物写进向量库。

写路径最值得讲的是它**不重复做昂贵的事**:embedding 调用是这里唯一慢的一步,所以 sync 逐篇判断——内容没变就只补元数据;内容变了但这段文本的向量以前算过,就**复用旧向量重新挂键**,一次 embedding 都不发;只有真正的新内容才去算向量。配上一道严格的删除守卫(详见下文),写路径既增量、又不敢误删。

## 一次召回怎么流起来

把概念串成一条线(这就是 `memex recall "一句中文 query"` 整个怎么运作):

1. **planner 看 query**:有中文、没代码 token → 判为「中文低锚」,decide 抬高 semantic 权重。
2. **三条 lane 并行取候选**:lexical 从已编译语料按 BM25 取一批;semantic 把 query embed 成向量、查中央向量库取一批。
3. **加权 RRF 融合**:按上一步定的权重,把两个排名合成一个,取最终 top-k。
4. **富化**:给每条命中补上标题和来源路径,让结果对人/agent 可读。

整条读路径**没有任何写副作用**——不碰向量库的写、不触发删除。读就是读。

## 关键取舍与代价

设计的代价值得点明:

- **中央索引 = 单点新鲜度。** 所有仓编译进一个中央集合,检索快、跨仓召回干净;代价是**索引不会自己跟上源仓**——你改了 note 不 sync,召回里就是旧的。memex 是「索引时」快照,不是实时视图。
- **embedding 超时故意设得长。** 本地单线程 embedding 服务首次建向量很慢。客户端如果短超时就遗弃请求,服务端却还在磨那个被遗弃的请求,下一个请求继续排队——**短超时会自己制造队列雪崩**。所以这里宁可长等。代价:首次大批量 sync 会慢,这是对的慢。
- **删除有三道守卫,所以「清理」从不痛快。** sync 的 prune 绝不跨仓判删(只在本仓 identity 前缀内)、单仓待删超过一半直接拒绝(要人显式 `--force`)、且默认 dry-run。代价:你想清掉一批旧点,可能被守卫拦下要手动放行。这是有意的——**误删整仓知识的代价,远高于多按一次确认**。
- **note 的 identity 是位置派生的,没有手写 key。** 一条 note 的身份 = 仓 + 域 + 在域里的相对路径。好处:无需维护任何 ID 映射。代价:**移动文件或改域层级 = 换了身份**(旧的删、新的建),不是「同一条 note 改了路径」。

## 心智边界

memex 是「检索引擎」,别把它想成别的:

- 它**不是知识库本身**——note 的真相在各源仓,引擎只消费它们的已编译产物。
- 它**不校验 note 正文**——frontmatter 合规与否归上游 authoring 工具,引擎只编译合规的、跳过不合规的。
- 它**不存源仓清单的真相**——哪些仓该被索引,定义在引擎外的一份清单里,引擎只读它、并在它缺失/损坏时 fail-safe 降级,绝不自己造一份真相。
- 它**不实时**——见上文,索引是 sync 时的快照。

还有一个实现边界值得知道:memex 刻意做成**纯 Python(无原生扩展)**。一个现实动机是分发——**本地安全软件常会重扫每一个新出现的二进制**,一个频繁迭代的原生二进制每次都触发重扫、拖慢首次启动;纯 Python 绕开了这层摩擦。这不是性能选择,是分发摩擦的选择。
